# Notice marks: the "!" and "?" actions, per monster

Generated by the scratch pair `notice.py` / `dropres.py`.  Every number below is read out of
`C:\MHGU-ROM\exefs\main.{text,rodata,data}` and the monsters' own
`enemy\cmd_tbl\*_cmdtbl.emc`.  Nothing is inferred from a neighbour.

## How each number was got

1. **The class.**  `build/arm/dti.json` lists every reflected class.  The ENEMY vtable is *not*
   the DTI `mtVtable` (that address holds unrelocated zeros in `.data`); it is the vtable whose
   slot `+0x14` holds the class's getDTI thunk -- the 3-word PIC thunk
   `ldr r0,[pc,#imm] / ldr r0,[pc,r0] / bx lr` whose literal resolves to that class's DTI.
   Action main is vtable `+0x1f4`.  98 uEm classes resolve this way, each to a unique vtable.
2. **The code block.**  The spawn table at **0x172ae2c** is 137 DTI pointers followed by 137
   pointers to that slot's CRO module name.  A module can hold two classes with their code
   interleaved (`roEm019.cro` = uEm019_00 + uEm020_00, `roEm087.cro` = uEm087_00 + uEm088_00),
   so the block has to be bounded per module, not per class -- bounding uEm019_00 on its own
   gives a 0x18-byte range and every one of its actions then reads as "plays nothing".
3. **Which class a monster without one of its own uses**, from that class's own tests on the
   em-number byte `enemy+0xb5f4` (`movw rN,#0xb5f4 / ldrb / cmp #imm`):
   em002 -> uEm001_00, em005 -> uEm004_00, em015 / em016 / em034 -> uEm014_00,
   em062 -> uEm060_00, em072 -> uEm071_00.  `+0xb5f5` is the `_NN` variant suffix, corroborated
   the same way (uEm023_00 tests 0/3/5, uEm043_00 tests 5, uEm079_00 tests 4, ...).
4. **The action.**  Command group 4 stream 0, parsed with the descriptor table at 0x172bc8c and
   the length rule at 0x50c24.  Op `00 <status> <number>` is the action op; its handler is
   **0x8456c** (walker jump-table base 0x836f0, entry 0x00), which calls **0x754b8** -> 0x76098
   with (status, number).  `00 00 ff` is not an action: that pair is special-cased at 0x84608
   into **0x75f4c** (clear / return to default).
5. **The motion.**  The class's action main run under unicorn with `enemy+0x73e0` = status,
   `+0x73e1` = number, `+0xb5f4/+0xb5f5` = em / variant, phase 0, posture 0; code inside the
   class's module block runs, every call outside it returns 0.  Stop at the first `setMotion`
   (0xafce8 / 0xafe84 / 0xafe8c / 0xafef0, r1 = (list << 8) | motion).  Same method as
   `efx/agents/*/actprobe.py`, and it reproduces the worked example exactly:
   uEm077_00 (2, 9) -> **L0 M5** blend 6.  Two spot checks against already-wired Seregios rows
   also match: (1, 9) -> L0 M4 blend 10 (rage) and (0, 2) -> L0 M14 (tired idle).

## Three corrections to the shared-code reading

**(a) Op `00` ends the walk; it does not fall through to the next op.**  Its handler sets the
walker's "issued" byte `sp+0x1ff` to 1 at 0x8595c and branches to 0x854f0, where the test at
0x854fc jumps to **0x861f0, which pops and returns**, handing the caller the stream cursor
`r0 = [r4]`.  The cursor lives in memory, so the walk RESUMES there next time.  Group 4 stream 0
is therefore a *sequence* of actions performed in order, and "its final action" means the last
step of the sequence -- not the only step that runs, and not a fall-through.

That distinction is what makes the Seregios example work rather than a coincidence: (2, 1) is a
real first step, it just plays no clip.  It calls only 0xbc7f4 (a getter) and 0x7a258 and
returns -- no setMotion on any path, at any posture 0..4 -- so (2, 9) is the step you can see.
**49 of the 94 ids have exactly that shape**: a status-2 action that plays nothing, then an
action that plays a clip.

**(b) 0xbd4f0 does not go through 0xbcae0.**  It sets the sleep flag `[+0x1428]+0x522 = 1`,
zeroes `+0x5cd4`, returns early if `+0x2c0` is already 0, and otherwise calls 0xc4298(e, 0xff)
and then **0xa4388(e, 0) directly** at 0xbd540, writing `+0x2c0 = 0` and `+0x2c4 = 0` itself.
Enumerating callers of 0xbcae0 therefore misses it.  The complete set of awareness-0 sites is
"callers of 0xbcae0 with r1 == 0, plus 0xbd4f0", and that set is closed: 0xa4388 has exactly
two callers in the whole binary -- 0xbcb2c inside 0xbcae0, and 0xbd540 inside 0xbd4f0.

**(c) There are other drop paths, and one of them IS reachable from the command table.**
Callers of 0xbcae0 with newState 0:

| site | what it is | action of its own |
|---|---|---|
| **0x84e70**, in the walker's handler for **op 0x6b** (0x84e3c) | zeroes `[+0x1428]+0x24c..0x24f`, then drops awareness; it *clears* `sp+0x1ff` and branches to 0x854f0, so the stream CONTINUES | **yes** -- the action ops that follow it in the same stream.  This is the drop column below |
| **0x8bfdc**, in 0x8b1fc, reached only from **op 0x97** (handler 0x852a8) | one outcome of a larger routine | no -- op 0x97 is the last op of its stream in all 66 tables that carry it (`97 00 \| ff`), so no action follows |
| **0xc8de0**, in 0xc8d20 | the awareness **timeout**: gated on the float `[+0x1428]+0x2c4` exceeding a limit read as a short from `0x71248(e)+2`; then 0xc975c | no |
| **0xa5ca4**, in 0xa5b84 | gated on `[+0x1428]+0x1a8 & 9 == 9`; then 0xba7b8(e, 0) | no |

| 0x7e280, 0x7e70c, 0x7fd20, 0x9ad2c, 0x9afe4, 0x9c1d8, 0x9c988 | r1 == 1 | not a drop |
| 0x7ea6c, 0x7ee24 | r1 == 2 | not a drop -- these are notices |

Class-local callers with newState 0: **uEm009_00** 0xd535e4 and 0xd537cc, **uEm012_00**
0xd7a23c, **uEm087_00** 0x10b1404 and 0x10bd590.  Every other class-local caller of 0xbcae0
passes 1.  None of those five is an action entry point.

## READ THIS FIRST: the actions are right, the motions are right, and most of them still
## cannot carry the mark

Raven, in the viewer: "Rathian, I don't see the ! icon or alert behavior. It's simply the start of
the walk animation", and "Seregios L0 M18 is the falling asleep animation".  Both are correct, and
auditing them turned up the real result of this whole exercise.

**What held up.** Group 4 stream 0 is exactly the right place, and it is now confirmed from the
ROM rather than taken on trust.  In 0x7e9c8, the notice path calls `0xbcae0(e, 2)` at 0x7ea6c --
the awareness write that fires effect 22, the "!" -- and then, twenty instructions later, hard-codes
the group and stream it will run:

    0007ed1c  mov  r0, #4            ; group 4
    0007ed24  strb r0, [r7]          ; -> enemy+0x72fc, the current group
    0007ed28  strb sb, [r5]          ; sb = 0  -> enemy+0x72fd, the current STREAM
    0007ed2c  movw r0, #0x72f4
    0007ed30  ldr  r0, [r4, r0]      ; the group table
    0007ed34  ldr  r0, [r0, #0x10]   ; +0x10 = group 4
    0007ed38  ldr  r0, [r0]          ; +0 = stream 0
    0007ed3c  str  r0, [r6]          ; -> enemy+0x72f8, the cursor the walker advances

Every group selection in the binary, paired with the awareness state written just before it:
group **4** for newState 2 (0x7ea78, 0x7ee30), group **5** for newState 1 (0x7e28c, 0x7e718),
and groups 3 / 6 / 7 / 11 / 17 elsewhere -- 6 being the rage group the Seregios notes already name.
**No group is selected on newState 0 at all**, which is the first half of the "?" problem.

The motions held up too: all 123 resolved clips **exist in the monster's own list** in
`docs/monsters.json` (zero missing), and re-probing every notice action across all 512
combinations of posture 0..7 x part 0..7 x direction 0..7 gives the **same clip every time** for
all 88 -- so the zeroed state is not hiding a branch.

**What does not hold up is treating the clip as a key.** Sweeping all 2048 actions (status 0..7 x
number 0..0xff) per class and counting how many route to each clip:

* **Rathian's L0 M5 is played by 9 different actions** -- (2,0), (2,7), (2,9), (2,0xb), (2,0x12),
  (2,0x13), (2,0x18), (2,0x1a), (2,0x1c) -- and the clip is `Motion[5]_start` 0.133s +
  `Motion[5]_loop` 2.4s, the shape of locomotion, not of a reaction.  Hanging c 1200 on
  `0|Motion[5]` fires the "!" on all nine.  That is what Raven saw.
* **Seregios's L0 M5 is played by 10.**  The worked example has the same fault; it was not a
  special case that happened to work.
* The worst are Nerscylla L0 M6 (**25 actions**), Duramboros L0 M6 (21), Nibelsnarf L0 M2 (20),
  Deviljho L0 M6 (17), Basarios / Gravios and Great Maccao (12), Bulldrome L2 M2 (11).

So for most of the roster **there is no alert animation**.  The monster notices, and group 4
stream 0 tells it to face the hunter and walk at it; the mark is drawn over its head by
0xa4388 on the awareness edge, not by anything in the clip.  The `shared by` column below is
therefore the column that decides what is wireable, and the `kind` column corroborates it:
a `one-shot` played by one action is a real reaction, a `loop` played by nine is the walk.

**The "?" reads differently, and Raven's sleep observation is the ROM being consistent.**  Since
no command group is selected on newState 0, there is no "?" reaction stream anywhere.  What the
op-0x6b column actually finds is the behaviour that was *already running* when awareness dropped
inside it -- and for Seregios that stream (g1 s142) is the go-to-sleep behaviour, so (1, 6) L0 M18
is the bedding-down clip.  The Seregios notes predicted this: "a monster that beds down while
aware plays the '?' on the way down."  It is a true site, just narrower than "drop": it is the
sleep "?", not a lost-interest one.  It is also mostly **unique** -- L0 M18 is played by exactly
one action -- so unlike the "!", several "?" rows are safe to wire as they stand.

## One place where "the final action" needs your judgement, not mine

Seregios's group 4 stream 0 ends ON the notice clip, so "the final action" is unambiguous there.
**16 ids are not like that**: their stream has one more step after the reaction, and that
step is a status-0 or status-1 action that plays the walk or the combat idle -- Basarios and
Gravios end `(2, 0) L0 M5` then `(1, 2) L0 M2`; the drome family (Velocidrome, Gendrome, Iodrome,
Giadrome) ends `(2, 1) L0 M8` then `(1, 5) L0 M2`; Daimyo Hermitaur and Shogun Ceanataur, with
their deviants, end `(2, 1) L0 M4` then `(1, 4) L0 M14`.  Taking the literal final action there
gives you the idle, not the "!" clip.

So the table carries **both** readings and I have not collapsed them:

* `final` -- the last action op in the stream that resolves to a motion.  This is your stated
  rule, and for 60 ids it is also the last status-2 action, Seregios among them.
* `last (2,x)` -- the last status-2 action that resolves to a motion.  Status 2 is the reaction
  family (Seregios's own notice is (2, 9); rage is status 1, issued from group 6).

Where the two columns differ I would wire `last (2,x)`, but that is a judgement about what the
status byte means, not something the ROM states, so it is yours to make.  Twelve ids have no
status-2 motion at all -- for those the `final` column is all there is, and where it is L0 M2
(Barroth em044_00, Brachydios em063_00 / em063_05) it may well be the idle again rather than a
reaction.

## What is actually wireable

Only rows whose clip is played by exactly ONE action can carry a record on the motion.

## Where it does not resolve, and why

Six ids, each for a different reason, and none of them substituted:

* **em012_00** -- `em012_00_cmdtbl.emc` has **no streams at all in group 4** (`cnt = 0` in the
  group descriptor at file +0x10 + 4*16).  There is no notice action to map.  Its c.pel does
  carry 1200 / 1201, so the records exist with nothing in the table to hang them on.
* **em033_00** -- group 4 stream 0 is `0c 00 | 0c 01 04 | 14 00 | 0c 02 | 0c ff | 14 2c |
  00 00 ff`.  The one op-00 in it is the `(0, 0xff)` clear (0x84608 -> 0x75f4c), not an action.
* **em050_00** -- group 4 stream 0 is `0c 00 | 0c 01 01 | 0c 01 03 | 14 09 | 0c 02 | 14 00 |
  0c ff`: **no op-00 anywhere**.  Only the 0x0c switch and two 0x14 registrations.
* **em084_00** -- group 4 stream 0 is `00 00 ff | ff`: the clear and nothing else.
* **em087_00** -- group 4 stream 0 is `ff`, the terminator alone.  Consistent: it is the one
  monster in `dev/effects-triage` whose c.pel carries **neither** 1200 nor 1201.
* **em038_00** -- the only action op is `(2, 2)`, and it resolves but plays nothing: the run
  reaches no setMotion on any path with the state zeroed.  So the action is known and the
  motion is not.
* **em011_00, em017_00, em025_00, em030_00, em037_00 / em037_04, em044_00, em057_00 /
  em057_04, em058_00, em063_00 / em063_05** -- these resolve, but to a status other than 2
  (see the judgement note above), so how much they are the reaction clip rather than the
  follow-on is not something the ROM settles.

Two partial gaps that do **not** affect any answer above:

* **em010_00 (5, 0x1e)**, **em046_00 (5, 0x13) / (5, 4) / (5, 0x1f)**, **em047_00 (5, 0) /
  (5, 0x1b) / (5, 0x1a)** fall through their class's unique-action switch to the "unhandled"
  default at 0xca050 / 0xca05c with the name `emUniqueActMain`: status 5 is dispatched
  somewhere other than action main, which this run does not enter.  In all three monsters the
  status-2 action that carries the answer resolves normally.
* **uEm019_00 / uEm020_00** share `roEm019.cro` and their code is interleaved, as do
  **uEm087_00 / uEm088_00** in `roEm087.cro`.  Bounding those classes separately gives
  uEm019_00 a 0x18-byte code block and makes all four of its actions read as "plays nothing";
  the numbers in the table are from the per-module block, and em019 / em020 / em088 do
  resolve.  Worth knowing if you re-run this with a per-class range.

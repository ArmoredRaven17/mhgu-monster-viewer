# Rajang (em023_00) and Furious Rajang (em023_05): when the beam fires

Class `uEm023_00` (vtable `0x17b22a8`, action main vt+0x1f4 `0xdecf14`) runs both. The variant byte `e+0xb5f5` is 0 for
Rajang and 5 for Furious. Both arcs ship the same `em023_00_cmdtbl` (md5-identical). The beam class is `uShellEm023_sp_02`:
id **0xa9** for variant ≠ 5 and **0xad** for variant 5. **0xaa / 0xae are NOT the beam**: they are `uShellEm023_sp_22`
(base22), spawned by vt+0x204 and `0xdec968`, which is what `states-em023_05.md` §1.5 describes. I opened that note before
reading. Beams Research agent (group B), 2026-09-30. Static read, with a harness cross-check.

Notes on the rows:

- For both Rajangs the beam is the same per action. Only the id differs: `0xde8924` `ldrb [e+0xb5f5]`, then `0xde8940` `cmp #5` → 0xad, else 0xa9.
- Every row plays a **single** motion: setMotion0, no partner.
- L2 M8 / M20 / M21 loop. Each function counts `P+0x1a2` = 2 motion-ends before L2 M9 (`0x209`) and vt+0x3dc. The frame gate lies in the `_start` piece, so it fires once per action.

## 2. Call chains

- **Ids.**
  - vt+0x158 `0xde1a20` registers 0xab..0xae (variant 5) or 0xa7..0xaa.
  - The beam ids appear as literals only there (`0xde1a70` / `0xde1ab8`) and in `0xde8908` (`0xde8948` / `0xde8970`).
- **Submits.** 6 submits in the band, each with its allocator (balanced):
  - **beam**: `0xde89d0` (tail `b`, in `0xde8908`, allocator `0x3fb7bc` with size 0x30);
  - base01 0xa8/0xac: `0xde82e0`;
  - base00 0xa7/0xab: `0xde86a0`;
  - base22 0xaa/0xae: `0xde24a8`, `0xdeca6c` (allocator `0x40ad58`);
  - a shell's second generation, 0x40 request: `0xdee498` (out of the class's code, after `0xdee058`).
- **Callers (whole-image branch + data census).**
  - `0xde8908` ← `0xde883c` (in `0xde86c0`) and `0xdea184` (in `0xde9fc4`).
  - `0xde86c0` ← arms (7,6) / (7,0xa) / (7,0x3e).
  - `0xde9fc4` ← (7,0x34) / (7,0x35) / (7,0x3f) / (7,0x40).
  - All of these sit in the status-7 dispatcher **`0xdeada8`**: `[e+0x73e1]`, 83 entries (0..0x52), default `0xdeb1a4`. It is reached from action main `0xdecf14` → status 7 → `0xdecf8c`.
- **`0xde86c0(e, r5)`:**
  - writes `e+0xb5f8` = (r5 == 2 ? 2 : 1);
  - phase 0: `P+0x1a1` = 1, `0xbc7f4(e,0)` (posture 0), setMotion0 L2 M8. It aims a pitch to the target (clamped −0xe39 / +0xaab) into `ctl+0x24` (`0xde88b0`) and sets `P+0x1a2` = 2;
  - phase 1: r5 ≠ 2 → gate 80 → spawn; gate 74 → `0x7ded8(e,0,0x14)`; on two motion ends → L2 M9.
- **`0xde9fc4(e, r6 = side, r5 = no-beam)`:**
  - phase 0: posture 0; L2 M21 (r6 == 1) or L2 M20; turn setup `0x7a258`; `P+0x1a3` = 1, `P+0x1a2` = 2;
  - phase 1: turn window `0xb0968` mode 9, 74..88 (`0xdea128`); r5 ≠ 1 → gate 74 → spawn mode 0; gate 104 → hit; `0x5393d0(e, 0.95 / 0.85 / 1.0)` once the frame reaches 0 / 70 / 104 (mode-1 queries; what `0x5393d0` does is NOT READ); two motion ends → L2 M9 (blend 2).
- **Remap vt+0x1fc `0xde1f50`** (status 7, numbers 4..0x3b, table `0xde1f84`), applied only when `0x81614` (tired) == 1: (7,4)/(7,0xb) → (7,0x42); (7,5)/(7,0xc)/(7,0x3b) → (7,0x43); **(7,6)/(7,0xa) → (7,0x3e); (7,0x34) → (7,0x3f); (7,0x35) → (7,0x40)**.

## 3. Unresolved, named

- **Mode 2 (from (7,0x06)) and BEAM_TYPES.** `em023_00:0` / `em023_05:0` carry mode 0's sh (life 133, flag-bit-3 start 33.0). Mode 2's own sh is [300, 6400, 0, −20, 15]. A viewer that fires (7,0x06) as `:0` gets the right effect with the wrong life and tracking start.
- **The EMC streams' own conditions** (op 0x83 / 0x6f / 0x2e in s11, s20, s24) are NOT READ. Which stream the AI runs, and so which of (7,0x34) / (7,0x35) it plays, is decided there.
- **`e+0xb5f8`** (written 1 or 2 by both functions) is NOT READ. It is not the beam.

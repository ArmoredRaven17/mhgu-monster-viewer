# Daimyo Hermitaur (em019_00) and Stonefist Hermitaur (em019_04) — when the beam fires

One class, `uEm019_00` (vtable `0x17ad418`, action main `0xdc0788` = vtable +0x1f4; its code shares the group band
`0xdb3e64..0xdce790` with `uEm020_00`), the variant byte `e+0xb5f5` choosing the monster: 0 = Daimyo, 4 = Stonefist.
Beam shell `uShellEm019_sp_02`, global id **0x9a** (Daimyo) / **0x9c** (Stonefist), read from the enemy slot
`[e+0xcacc]`, which vtable +0x158 `0xdc09d4` fills (0x99 / 0x9a / 0x19d, variant 4: 0x9b / 0x9c / 0x9d —
`E:\offline\decode\notes\states-em019_00.md` §1.4). Beam research agent A, 2026-09-30. Method and positive control
(Basarios's beam reproduced through the same harness): `dev/beams/em005_00.md` section 5. Both monsters play list 2
from `em019_00_2` (Stonefist's list 2 is `shared`).

**The spawn itself has no frame test.** Every beam goes through one helper, `0xdb9a88(e)`, which makes the request at
once; its callers decide when. There are exactly two: the status-7 beam function `0xdbbff0` (at f96) and the status-2
turn function `0xdb8d58` (at the turn's first frame, only if no beam was made since the beam action started).

**`ctl+0x52`, the "beam made" latch.** Set to 1 only by `0xdb9a88` itself (`0xdb9aa0`). Cleared by the class setup
`0xdb3f84` (`0xdb41f4`) and by the on-action-start hook, vtable +0x204 `0xdb4474`, for status 7 numbers **3, 0x1a,
0x1c, 0x2e, 0x2f, 0x31** — exactly the six beam actions (its status-7 table `0xdb46c4`, index = number - 3; those six
entries -> `0xdb4780`: `ctl+0x52 = 0` at `0xdb478c`). No other writer (census of `+0x52` stores in the band).

**Which turn follows which beam** (phase 3 of `0xdbbff0`, `0xdbc258..0xdbc3e4`, after the motion ends, or at f135 for
(7,0x31) `0xdbc224..0xdbc254`): only when the byte `e+0x7420 != 0` (else L2 M54 is replayed from frame 130,
`0xdbc2e0..0xdbc304`). The side is the sign of (yaw to the target - `P+0x54`) (`tst r0,#0x8000`, `0xdbc2b8`):
(7,0x1a) -> (2,0x32) / (2,0x31); (7,0x1c) and (7,0x2f) -> Daimyo (2,0x23) / (2,0x22), Stonefist (2,0x32) / (2,0x31);
(7,0x31) -> (2,0x36) / (2,0x35); (7,0x03) and (7,0x2e) -> none (phase 2: L2 Motion[17] `0x211` blend 4, then
vtable +0x3dc). The issuing calls are `b 0x768c8` at `0xdbc2d8` / `0xdbc320` / `0xdbc364` / `0xdbc3a8` / `0xdbc3d0` /
`0xdbc3e4` (ROM-run with `e+0x7420 = 1`: exactly these, by target side).

**So in play:** not tired -> the beam at **f96** of L2 M18 / M54; the turn that follows does NOT make another one
(`ctl+0x52 = 1`). **Tired** (`0x81614`: `P+0x505 & 0xfe == 2`, rom-map row 502) -> no beam at f96, and if the turn
follows, **the beam is made at the turn's first frame instead** (`ctl+0x52` is still 0). Both halves READ and ROM-run;
whether `e+0x7420` is set for this class is not read (section 4).

Also written by both callers, read by neither: `e+0xb5f8` = 2 when tired, else 1 (rank <= 4) / 3 (rank > 4)
(`0xdbc038..0xdbc040`, `0xdb8dd8..0xdb8ddc`); no reader in the band (census) — its consumer is elsewhere and unread.

- **`e+0x7420`** (gates the turn after (7,0x1a) / (7,0x1c) / (7,0x2f) / (7,0x31)) is not read for this class.
  `E:\offline\decode\notes\states-em022_00.md` (lines 176, 542-543) reads it as written by `0xb1560`, 1
  unconditionally when `P+0x1a8` bit 3 is clear — for em022, not em019. If it is 1 here too, the turn always follows.
- The beam's own life across the motions: rom-map row "Em019 / Em056 +0x170" says a motion in 0x236..0x239 (L2 M54..M57)
  is taken as the spawn's, so the beam lives on through the turn; L2 M18 (0x212, (7,0x03) / (7,0x2e)) is outside that
  range. Not read here.
- `ctl+0x16` -> +0x24: what the beam does with the serial is not read (the turn also copies it to `P+0x9cc`,
  `0xdb93a0..0xdb93a8`).
- The (7,0x2e) / (7,0x2f) lead-in (L2 M61) is not issued by anything found.
- Whether the setup allocator clears +0x22..+0x23 / +0x28..+0x2b is not read (never written).

# Plesioth (em010_00) — when the beam fires

Class `uEm010_00` (vtable `0x179e2b8`, action main `0xd6a59c` = vtable +0x1f4, band `0xd618c8..0xd6cff8`). Beam shell
`uShellEm010_sp_02`, global id **0x7d**, written as a LITERAL by every spawner (`mov r0,#0x7d` / `mov r2,#0x7d`).
Beam research agent A, 2026-09-30. Method and its positive control (Basarios's beam reproduced through the same
harness): `dev/beams/em005_00.md` section 5. Every row was read at the consuming instruction and ROM-run from the
action main (section 5). Plesioth's lists: `em010_00_0`, `em010_00_2`, `em010_00_3`; every beam motion is list 2 and
is ONE clip in the viewer (no `_start` / `_loop` split).

## 1. The beam spawns

All seven spawners: phase machine on `P+0x1a1` (`P = [e+0x1428]`); phase 0 sets the motion, phase 1 runs the frame
gates; the spawn gate is `0xb0968(e, r1=0, r2=0, s0=F, s1=0.0)` = opcode 0 of `0x72714`, "the frame crossed F" (the
frame is `s0`, trap 21). **The mode is the only thing rank changes**: `questRank` (`0x3a8430`) `> 4` (G rank) picks the
second mode (`movwgt`). No tired, rage, variant or part test in any of them (census of their calls).

"X" = the mode's `_sh` vec 1.x (degrees; the base02 default reader's angles `+0x1680`); "origin" = sh vec 0 when it is
not (0, -48, 75). Per the coordinator, Plesioth's `+0x15c` `0xd6cd38` reads the setup's +0x20 as a u16 pitch word for
modes other than 2 / 4 / 13 / 17 / 19 / 28 — so of the three computed pitches above, (7,0x0d)'s and (7,0x28)'s are
consumed and (7,0x32)'s (modes 13 / 28) is not; (7,0x06)'s literal 0xe39 (modes 2 / 17) is not either. (That reader
is the coordinator's statement, not read here.)

**Per-mode looks** (arc `em010_00`, shell02 `_ef` / `_sh`): u 0 + impact u 1 = modes 0, 1, 3, 5, 6, 9, 10 ->
`em010_00:0`; u 10 + u 1 = modes 2, 4, 13 -> `em010_00:2`; u 20 = modes 15, 16, 18, 20, 21, 24, 25 ->
`em010_00:15`; u 30 = modes 17, 19, 28 -> `em010_00:17`. Every mode >= 15 has sh int 2 = 0, so its reader
(`0xd6caf0`) sets `+0x168c` and `+0x154` makes the u 21 child (rom-map rows). **Only modes 0 and 15 have sh int 1 = 0
(flag bit 0)**: BEAM_TYPES' `em010_00:0` / `:15` entries carry mode 0's / 15's flag 1, which the other modes of
those looks do not have; and the looks hide the per-mode angle X (0 .. 55 deg) and life (63 .. 130).

  f130..160 windows' value (`0xc0dbc`, `0xb0900`); not read. It does not touch the setup.

- Whether the setup allocator `0x3fb7bc` (the heap object from `0x7a75a0`, its vtable +0x20) clears the block is not
  read: the bytes +0x22..+0x23 and +0x28..+0x2b are never written by any spawner (the ROM-run fills the block with
  0xcd and they stay 0xcd).

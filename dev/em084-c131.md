# em084_00c 131 (em084_00_005): who requests it, and how it ends

Research agent, 2026-10-05. Brief: find every request site of Nakarkos's `em084_00c` key 131 and what ends it. The viewer
runs it as `"when": "calm"` (docs/effects/em084_00.json, effect 0), and `schedule.js setRage` hard-releases it when rage
turns on. Static reads with `efx/armdis.py` (and `armdis.sweep` for whole bands). Unicorn cross-check in scratchpad
`c131/emu.py`. `add_effects.py em084_00` was run with no flags. No recorder or lift was run.

Read first: rom-map "THE PSL ENABLE MASK" (rows `0x31cc70`..`0xca170`), row `0x328ba0` (sel 2 pinned on class
overrides), `dev/em084-class-effects.md` §0-§6, `dev/effects-triage/em084_00.md` row c 131, schedule.js header
(the walker and end modes, lifted from `0x31ca58` / `0x3295fc`).

## Answer

**c 131 is a PSL record, and nothing else requests it.** It is bound on two body PSL blocks. One of them names a motion the
game does not have. The live binding is **L0 Motion[67] bit 1, frames 0-19**. That motion is the whole of actions
**(6, 0x33)** and **(6, 0x34)**. The effect starts on the motion's first frame. It ends gracefully when the bit falls at
frame 20, which is the frame where c 123 (em084_00_006) fires on bit 0. **No rage or calm test exists anywhere on its
path.** In the viewer it is a `clip` record. It is not `calm`, and nothing should release it when rage changes.

## 1. The record (READ, data)

- `em084_00c.pel` (v15): RULED has 0 records, SEQUENCE has 19, UNIQUE has 13. **Key 131 exists only in SEQUENCE**:
  `effect\em\em084\em084_00_005`, joint 4, mode 0 / sub 1, pos (0, 0, 500), **end byte +0x3a = 1**, +0x3b = 0. The
  viewer's payload (em084_00.json effect 0, 160 bytes) carries the same values: +0x30 = 131, +0x32 = 4, +0x3a = 1,
  +0x3b = 0. `em084_00u` has no key 131 and no em084_00_005 in either array.
- The arms' `em084_00c_l` / `_r` also have a key 131. It is **em084_00_050**, a different record, and the arm PSLs fire
  it (class-effects §0: `[arm+0x1358]` is the arm's own c pel). Those rows are not this record.

## 2. Request sites

### 2a. The PSL: the only site (READ)

Every `.psl` of the monster was decoded (`dp.decode_psl`; block layout +0 mask, +4 u16 effectNo[32], +0x44 p1[32],
runs at +0x148). Body blocks whose effectNo is 131:

| file / slot | frames | bit | p1 | on | the slot's other bits |
|---|---|---|---|---|---|
| `em084_00_0.psl` slot 15 (L0 M15) | 381 | **0** | 3 (c) | f0-379 (one run, value 3) | bit 1 = c 135, also f0-379 |
| `em084_00_0.psl` slot 67 (L0 M67) | 433 | **1** | 3 (c) | **f0-19** (run value 2) | bit 0 = c 123 at f20 (run value 1) |

No block in `em084_00_2.psl` or `_3.psl` names 131. The `_l_*` / `_r_*` hits (L0 M17/40/67, L2 M9/10/64/67, L3
M5/7/10/54/57/59/63) all resolve in the arms' lists. **Control:** the same scan finds c 123 and c 135 on these blocks,
and the arm rows.

How a bit becomes a request (each step READ):
- Rise `0x31c980`: it calls the owner's `vt[+0x18]` with **`r1 = 1` (`0x31c9fc`), so sel 1 = SEQUENCE**, plus the block
  and the bit. Then it stores the bit's state word into core `+0x194` (`0x31ca14`).
- On Nakarkos's body vtable `0x17f11fc`, that window slot is `+0x12c` = **`0x6ff6c`** (word at `0x17f1328`).
- `0x6ff6c(e, sel, block, bit)` reads p1 = `[block+0x44+bit*4]`: 3 picks the c pel `[e+0x1358]`, 4 picks the u pel
  `[e+0xb624]`. The key is `ldrh [block+4+bit*2]`. Then it calls `e->vt[+0x138]` = `0x6fd8c`, and from there the
  generic request `0x53a7d8`.
- **The only gate in `0x6ff6c`:** action group `[e+0x73e0] == 0xc` with number `[e+0x73e1] == 0xff` returns 0 before
  any request (`0x6ffac`..`0x6ffd0`). There is no rage, tired, rank or part test there, and none in `0x6fd8c`.

### 2b. The enable word: bits 0 and 1 are always on (READ, emulated)

`0x7256c` zeroes `e+0x13f4` and then calls `vt+0x13c`. Nakarkos overrides that slot with **`0x106cae8`** (code ends at
`0x106cbb0`):
- It calls the base `0xca170` first. The base does `orr #0x3f` unconditionally (`0xca184`), then adds `0x1c0` calm,
  `0xe00` enraged, or `0x7000` tired and not enraged.
- The override only ORs further bits ≥ 15. It clears nothing:
  - L3 M63 (`0x33f`): `|= 0xf8000`.
  - L2 M23 (`0x217`) with action (7, n ≤ 7) where `0xfb` has bit n set: `|=` table `0x159bff0[n]`. The table is
    `0x38000` ×6, then `0x1c0000` ×2.
  - L0 M1 (`0x001`) during action (13, 0) (`0x6fe88`) with `[P]+0x1a1 == 4`: `|= 0x38000`.
- In the body band, `#0x13f4` appears only at those three ORs (`0x106cb44`, `0x106cb54`, `0x106cb98`).

So c 131's bits 0 / 1 fire calm, enraged and tired alike.

**Emulated** (`emu.py` (a): `0x106cae8` run on a zeroed enemy with Nakarkos's vtable):

| motion | calm | enraged | tired |
|---|---|---|---|
| 0x00f, 0x043 | 0x1ff | 0xe3f | 0x703f |
| 0x33f (positive control: the class arm runs) | 0xf81ff | 0xf8e3f | 0xff03f |

**Emulated** (`emu.py` (b): `0x6ff6c` on the REAL slot 15 / 67 blocks, with `vt+0x138` stubbed):
- L0 M15 bit 0 and L0 M67 bit 1 → `pel c(+0x1358) sel 1 key 131`, calm and enraged alike.
- Under (12, 0xff) → no request.
- Controls: L0 M67 bit 0 → key 123; L0 M15 bit 1 → key 135.

### 2c. Class code: no site (READ, with controls)

- **Every class or shared table path resolves UNIQUE.** All class request overrides pin sel 2 (rom-map `0x328ba0`), and
  Nakarkos's `0x106f890` tails to `0x6fdd4` with `r1 = 2`. `0x6fdd4` passes its `r1` as the sel (`0x6fe64`). c UNIQUE
  has no 131, so **no `vt+0x1cc` / shared-table request can reach this record, whatever id it uses**. The body's tables
  hold c {-1, 800, 1600, 1601} and u {-1, 90..96} (class-effects §0).
- **Body band `0x1064be0..0x107b29c`** (`armdis.sweep`, every word):
  - `#0x83` appears twice, and neither is a request. `0x1069c40` is a motion mask (`tst r3, r2, lsl r1` over
    `0x309+`). `0x107572c` is `0x6f618(e, 0x83)`, a tune read.
  - `#0x138` appears only as a stack size and `vldr`s.
  - There is no `bl` to `0x6fd8c` / `0x53a7d8` / `0x6ff6c` / `0x328ba0`. The only branches to `0x6fdd4` / `0x6feb8` are
    the overrides `0x106f8b0` / `0x106f8e0`.
  - **Control:** the same sweep finds every known request id: `#0x3e9..0x3ee` at `0x1067c4c`, `0x1067c68`, `0x10687c0`,
    `0x10687dc`, `0x1068850`, `0x106886c`, `0x10688e0`, `0x10688fc`, `0x106f1a4`, with their `[r0,#0x1cc/0x1d0]`
    loads (class-effects §1).
- **Whole `.text`: `movw #0x1358`** (the c pel field) appears 32 times. In the shared enemy range they are only:
  - `0x6fe40` (`0x6fdd4`, sel from its caller: sel 2 on every class override);
  - `0x70008` (`0x6ff6c`, the PSL start);
  - `0x70ce8` (the pel loader's store);
  - `0x72dbc`, the base unit's `+0x12c` window slot `0x72da4` (in 429 vtables). Nakarkos's vtable replaces it with
    `0x6ff6c`.

  The rest lie outside enemy code, plus the arm loader `0x107bd98`. **INFERRED** that none of the non-enemy hits touch
  an enemy, because their owners were not read.
- **Callers:** `0x6fdd4` has 11 callers: `0xa3dd4` (the shared tail), `0x106f8b0`, the arm `0x107fca0`, and other
  classes. `0x31c980` has 2: `0x40728` and the base sequence vtable.

### 2d. The part-break `.dtp` "131": a group id, not a key (READ, by class-effects §5)

`em084_00_dtbparts.dtp +0x64` rows (4,2,2,131) and (4,4,4,131) carry 131 in the group column. The shared break path
`0x99edc` → `0x9a00c` → `0xa442c(e, part, level)` builds id `part·5 + level + 6` and looks up the shared u table. For
part 4 that gives u 1021 / u 1023 (em084_00_100). The group column never becomes an effect key, and the break path
reads the u pel with sel 2. It cannot reach c SEQUENCE 131.

### 2e. Shared code, states and rage (READ for the path; the AI side not read)

- No shared request reaches c SEQUENCE 131: 2c covers the tables, the u 1120 / 1121 rage puff, and u 1400.
- The PSL path has no rage test (2a / 2b).
- What remains, and was NOT read: whether the EMC / AI picks (6, 0x33) / (6, 0x34) only in some states. That would
  change how often c 131 plays, not how a play starts or ends.

## 3. What starts and ends it

**L0 M67 is (6, 0x33) and (6, 0x34) (READ).**
- The group-6 dispatcher `0x1073214` jumps through a table at `0x107323c` (offsets added to `0x107323c`): index 0x33 →
  `0x1073424`, index 0x34 → `0x1073438`.
- Both call `0x1073604(e, 1, r2)`. `r2` is 0 for 0x33 and 1 for 0x34.
- Phase 0 sets `[P]+0x1a1 = 1`, then calls `0xbc7f4(e, 0)` and **`0xafe84(e, 0x43)` = L0 M67** (`0x1073668`). With
  `r1 == 0` it would set L0 M18 instead (`0x1073700`, index 0x01's path).
- It orders both arms (`0x106e238(e, 1|2, 1, n)`): n = 0x34 for (6, 0x33) and 0x38 for (6, 0x34).
- Phase 1 sets the rate, then on clip end (`0xb09c8`) calls `vt+0x3dc`, which ends the action.
- `build/hitzone-states/nak-clips.json` (emulated) agrees: `6/33` and `6/34` play `L0 M67` in both stances.

**Start (READ):** on the first walked frame of L0 M67, bit 1 rises and requests c 131. The new motion's first update
processes no frame (schedule.js, `0x31cb40`).

**End (READ for the bit and the end byte; the stop chain is the lifted transcription in schedule.js):**
- Bit 1 is on for f0-19 and falls at **f20**. There `0x31ca40` ORs 2 into the state word.
- The record's end mode 1 (core `+0xca` = pel `+0x3a`) stops the effect on bit-off or on a motion change. Its +0x3b of 0
  makes the stop graceful: the emitters stop and their particles run out.
- So c 131 is a **20-frame lead-in on (6, 0x33) / (6, 0x34)**. If the action is cut before f20, the motion change ends
  it.

**L0 M15 never plays (INFERRED, three independent negatives):**
- **`em084_00_0.lmt` has no motion 15.** Its pointer is 0. The `.lmt` holds 19 motions in list 0: 1-5, 8, 9, 14, 17,
  18, 40, 41, 50-52, 59, 63, 66, 67. PSL slots 15 (381 f), 64 (351 f) and 65 (351 f) are blocks with no motion. Every
  other PSL block matches its `.lmt` frame count, in lists 0, 2 and 3. The arc has no second list-0 LMT
  (`romfs/nativeNX/arc/enemy/em084_00.arc` is the only em084 arc).
- **No code sets 0x00f for him.** In a whole-`.text` scan for `mov(w) r1, #0xf` feeding `0xafe84` / `0xafce8` /
  `0xafe8c` / `0xafef0` / `0x7256c`, 34 sites appear, none in the body band `0x1064be0..0x107b29c` or in the shared
  range below `0x200000`. **Control:** the same scan for `#0x43` finds `0x107366c`, the site above. Nakarkos's data
  `0x17f1200..0x17f6494` holds no word 0x0000000f.
- **`nak-clips.json` (every g0/1/2/6/7/10/11/13 action, both stances) never lists L0 M15.** His group-0 dispatcher
  `0x106f9e0` handles numbers 0, 1 and 7 only. Number 2, the shared tired idle that is L0 M15 on Gammoth and others, is
  ended at once through `vt+0x3dc` = `0x75168`.

What is not read here: a table-driven shared setter with a register motion, and how the motion player treats an empty
slot. Both could only matter if a slot-15 motion existed.

## 4. What it means for the viewer

- **Correct `when` for c 131: `clip`.** It comes from `CLIP_EFFECTS em084_00 'L0 Motion[67]'` bit 1, key 131,
  efl em084_00_005, **on [[0, 20]]**, beside the existing bit 0 c 123 at [[20, 21]].
- `add_effects.py em084_00` already plans that row ("L0 Motion[67] | 433 | 1 | c 131 | 0-20 | ok | ok"). It is
  missing from monster.js only because the record is exported `calm`: CLIP_EFFECTS lists only records exported as
  `clip`.
- The plan's L0 M15 row ("the viewer has no L0 Motion[15]") should stay out. The game has no such motion either.
- **The hard release on rage should not exist for this record.** Nothing in the ROM ties c 131 to rage:
  - It starts only on an L0 M67 frame-0 rise, never on a state.
  - It ends by bit-off at f20 or a motion change, gracefully (+0x3b 0), and never by an immediate release.
  - The release the viewer does today is not a game behaviour. Calm → Enraged → Charge leaves a c 131 that the game
    would never have started. Charge rung → Enraged releases it mid-emission and reaches the unrecorded `0xa55ed4`
    branch of `0xa55ea8`.
  - With c 131 as a clip record, the State switch no longer touches it, so that crash path is no longer taken from the
    rage toggle. The `0xa55ed4` branch stays unrecorded, and a stop of any other record can still reach it. That is a
    separate open item and is not closed here.
- `calm` then has no user. em084_00.json is the only json carrying it. The schedule.js header comment that names
  "Nakarkos's charge aura, em084_00_060 on joint 0" as `calm` is stale twice over: u 90 is `event` (class-effects §2),
  and the `calm` entry was em084_00_005.

### Side finding (READ, out of scope)

Nakarkos's `vt+0x13c` (`0x106cae8`, §2b) enables **L0 M1 bit 15 (c 140, em084_00_008)** only during action (13, 0)
with `[P]+0x1a1 == 4`. The viewer's CLIP_EFFECTS fires c 140 on every L0 M1 play, because the file mask is `0x8000`
and em084_00 is not in `PSL_MASK_MONSTERS`.

It also enables bits 15-19 on L3 M63 and bits 15-17 / 18-20 on L2 M23 per (7, n). L2 M23's file mask is `0xc8000`:
bits 15, 18 and 19 are c 135, u 205 and u 206. Which (7, n) enables which of them is §2b's table, and the viewer does
not apply it.

## 5. What the viewer should do

1. Re-export c 131 as a clip record: `export_effects.py em084_00 aura ... record=em084_00c:131@clip` in place of `@calm`.
   Then regenerate CLIP_EFFECTS with `add_effects.py`, so L0 Motion[67] carries `{ bit: 1, key: 131, on: [[0, 20]] }`.
   (Recording or lifting, if needed, needs the efx slot announced.)
2. Drop the `calm` path for this monster. No json uses it after step 1. `setRage` should not touch c 131 at all.
3. Optional, separate: add em084_00 to `PSL_MASK_MONSTERS` with the `0x106cae8` arms above, so c 140, the L2 M23 and the
   L3 M63 bits ≥ 15 fire only where the game enables them.
